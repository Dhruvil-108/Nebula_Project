# UI Theme, Component and UX Guardrails: Nebula Premium Light 2.0

## STEP 0 (once, before any UI work)
Audit the existing UI and write `docs/recruitment/UI-DESIGN-SYSTEM.md` describing what actually exists: the Tailwind config and CSS variables (colors, fonts, radii, shadows, spacing), how the brand orange (`#f97316`) and warm surface (`#FBF8F4`) are used, and every reusable component in the app and in `Frontend/src/components/recruitment` (`CandidateDrawer`, `CandidateStagePill`, `JobStatusPill`, `RecruitmentKanban`, `CreateJobModal`, `AddCandidateModal`, `ScheduleInterviewModal`, `ScorecardModal`, `CreateOfferModal`, `OnboardEmployeeModal`, `LinkedInPostModal`, plus shared buttons, inputs, selects, tables, cards, toasts, empty states and skeletons). For each, record file path, props and variants. This document is the source of truth for all new UI. Show it for approval.

## HARD RULES
1. **Theme**: light only (Nebula Premium Light 2.0). Use existing design tokens and Tailwind classes. No hard-coded hex values, no inline color styles, no new palette, no dark mode.
2. **Reuse before creating**. Search for an existing component first. If a new one is needed, build it from the same primitives, place it next to its siblings, and match the prop style, naming and variant pattern. New stage or status pills extend the existing pill pattern (same size, radius, typography, color-coding approach).
3. **No new UI library** (component kits, icon packs, chart libraries) without approval. Use the icon set and charting approach already in the project (`lucide-react`, `recharts`).
4. **Layout patterns**: pages use the same page shell, header, filter bar and spacing rhythm as existing recruitment pages. Detail views open in the right-side drawer pattern (like `CandidateDrawer`). Create, edit and confirm flows use the modal pattern (like `CreateJobModal`). Multi-step flows reuse the existing wizard pattern. Add new pages to the existing sidebar group and the `/dashboard/recruitment` route structure; do not invent new navigation patterns.
5. **Motion**: Framer Motion only, reusing the durations and easing of existing drawers, modals and badges. Subtle and purposeful, honoring `prefers-reduced-motion`. No decorative or looping animation.
6. **States**: every data view has a loading state (skeleton matching the layout), an empty state (icon, message, primary action), an error state (message and retry) and a permission-denied state. Every mutation shows a pending state on its button and a success or error toast using the existing toast system.
7. **Forms**: same field components, label placement, required markers, inline validation messages and disabled or pending behavior as existing modals. Use the same schema-validation approach as the rest of the app.
8. **Data display**: tables get sticky headers, pagination, sorting and bulk selection in the style of existing tables. Currency, number and date formatting use the shared formatters. Times display in the organization or user timezone.
9. **AI UI**: all AI-generated content carries one shared `AiBadge`, shows a loading state, and can be regenerated, edited, accepted or discarded; it never applies itself. Explanations and confidence sit in a collapsible 'Why' section. Build one shared `AiPanel` component for the whole module.
10. **Responsive and accessible**: works from 360px up to desktop; fully keyboard navigable; visible focus rings; WCAG AA contrast on the warm surface (check text in brand orange and use orange for fills and accents where small text would fail); aria labels on icon-only buttons; focus trapping in modals and drawers; drag-and-drop has a keyboard alternative.
11. **Performance**: virtualize long lists and boards, lazy-load route pages, debounce search, avoid layout shift.
12. **Consistency check before finishing any screen**: compare it side by side with two existing recruitment screens (spacing, type scale, colors, radii, shadows, icon size) and fix differences. Capture a screenshot of each new screen, including its empty, loading and error states, for the walkthrough.
